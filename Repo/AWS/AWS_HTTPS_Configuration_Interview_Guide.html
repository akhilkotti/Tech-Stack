1. Why Do We Need to Configure HTTPS?

Interview mindset: Don't start by explaining AWS console clicks. Start with the business and technical reason for configuring HTTPS.
“My responsibility was to expose the application through a secure HTTPS URL rather than allowing users to access it through plain HTTP. HTTPS protects communication between the end user and the application using TLS encryption and also allows the browser to verify the server's identity through a trusted certificate.”

HTTP vs HTTPS

User→HTTP : 80→Application

With plain HTTP, the connection is not encrypted. Sensitive information could potentially be exposed while travelling across the network.

With HTTPS:

User→HTTPS / TLS : 443→Secure Endpoint

HTTPS provides:

  • Encryption – protects data while it travels over the network.
  • Authentication – the certificate helps prove the server's identity.
  • Integrity – helps prevent traffic from being altered in transit.
  • User trust – browsers recognize a valid certificate and secure connection.

2. Why Do We Need an SSL/TLS Certificate?

A TLS certificate is required for a trusted HTTPS connection.

Example

User enters:

https://www.equitek.net

The browser needs to determine whether the endpoint is legitimately authorized for www.equitek.net.

A certificate contains information such as:

  • Domain name(s)
  • Certificate authority / issuer
  • Validity period
  • Public-key information
“The certificate allows the browser to establish trust with the HTTPS endpoint. If the certificate is invalid, expired, or doesn't match the hostname, the browser can display a security warning.”

4. Why Add Both equitek.net and www.equitek.net?

These are separate hostnames:

equitek.netwww.equitek.net

If users can access the application through both URLs, the certificate should cover both names.

Certificate coverage 
Certificate
 ├── equitek.net
 └── www.equitek.net
“We included both the root domain and the www subdomain in the certificate because we wanted HTTPS to work for both hostnames.”

Alternative: Wildcard Certificate

For appropriate architectures, a wildcard certificate can cover subdomains:

*.equitek.net

This can cover hostnames such as:

www.equitek.net
api.equitek.net
test.equitek.net

5. Why Does ACM Create CNAME Records?

ACM needs to verify that you control the domain. This is called domain validation.

ACM→DNS Validation CNAME→Route 53→ACM Validation→Certificate Issued

Typical Flow

  1. Request a public certificate in ACM.
  2. Enter the required fully qualified domain names.
  3. Select DNS validation.
  4. ACM generates validation CNAME records.
  5. Create the records in Route 53.
  6. ACM checks the DNS records.
  7. The certificate changes from Pending validation to Issued.
“ACM uses DNS validation to verify domain ownership. Since the domain is hosted in Route 53, we can create the validation records there. Once ACM validates the records, the certificate becomes Issued.”

6. Why Do We Need Route 53?

Route 53 is being used primarily as the DNS service.

www.equitek.net→Route 53→CloudFront

DNS translates a human-friendly domain name into the AWS destination where traffic should be routed.

Without a custom DNS name 
d1sw29gbt5oue5.cloudfront.net
Business-friendly URL 
www.equitek.net
Important distinction: Route 53 does not provide the HTTPS encryption itself. Route 53 handles DNS. ACM provides the certificate, and CloudFront can terminate the HTTPS connection.

8. Why Configure “Redirect HTTP to HTTPS”?

Suppose a user enters:

http://www.equitek.net

We want the user to automatically move to the secure URL:

https://www.equitek.net
HTTP Request→CloudFront→HTTP → HTTPS Redirect→Secure HTTPS Request
“We configure the viewer protocol policy to redirect HTTP to HTTPS so that users are automatically moved to the secure version instead of continuing to use an unencrypted HTTP connection.”

9. Why Configure an Alternate Domain Name?

CloudFront automatically provides a distribution domain:

d1sw29gbt5oue5.cloudfront.net

But users should access the business domain:

www.equitek.net

Therefore, the CloudFront distribution is configured with an Alternate Domain Name (CNAME).

CloudFront→Default Domain CloudFront→www.equitek.net
“CloudFront needs to know that traffic arriving for www.equitek.net belongs to this distribution. The alternate domain name provides that mapping.”

10. Why Is S3 Used as the Origin?

In this architecture, S3 stores the static website content.

index.html
css/
js/
images/
fonts/

CloudFront retrieves that content from S3 when it is not already cached.

Browser→CloudFront→S3→Static Content

S3 is useful for static content because it provides durable object storage without requiring us to maintain web servers for the static assets.

11. Important Technical Correction About the S3 HTTPS Step

Do not repeat this part of the original notes exactly in an interview.

The notes say to change S3 Static Website Hosting from HTTP to HTTPS. The S3 static website endpoint itself is HTTP-only. If CloudFront is configured to use an S3 website endpoint as the origin, HTTPS is not used between CloudFront and that website endpoint.

Important Architecture Distinction

Browser
   |
   | HTTPS
   ↓
CloudFront
   |
   | HTTP when using S3 website endpoint
   ↓
S3 Static Website Endpoint

The important security point in this architecture is that the viewer-facing connection is HTTPS. If HTTPS is required from CloudFront to the origin, use the appropriate S3 REST endpoint and CloudFront/S3 configuration rather than the S3 static website endpoint.

Interview-safe wording:
“The important HTTPS termination point in this architecture is CloudFront. The viewer connects to CloudFront over HTTPS using the ACM certificate, while S3 provides the static content as the origin.”

12. Do We Need Two CloudFront Distributions?

Important: Two hostnames do not automatically require two CloudFront distributions.

A single CloudFront distribution can support multiple alternate domain names when the architecture allows it.

CloudFront Distribution
       |
       ├── equitek.net
       └── www.equitek.net
       |
       ↓
      S3

Separate distributions may make sense when domains require different:

  • Origins
  • Cache behaviors
  • Security policies
  • WAF configurations
  • Deployment lifecycles
  • Application architectures
Interview recommendation:
“We can use CloudFront with alternate domain names for the required hostnames. Separate distributions may be used when the domains require different origins, behaviors or security configurations.”

13. Why Configure Route 53 Alias Records?

After CloudFront is created, AWS provides a domain such as:

d1sw29gbt5oue5.cloudfront.net

But users should access:

https://equitek.net
https://www.equitek.net

Therefore, Route 53 maps the custom domain to the CloudFront distribution.

equitek.net→Route 53 A/AAAA Alias→CloudFront
www.equitek.net→Route 53 A/AAAA Alias→CloudFront

An AWS Alias record allows supported AWS resources, including CloudFront distributions, to be targeted from DNS records.

16. HTTPS Troubleshooting Scenarios

Scenario 1 – ACM Certificate Stays Pending Validation

ACM→Validation CNAME→Route 53

Verify that the DNS validation CNAME exists and is correct.

Scenario 2 – Certificate Issued but CloudFront Rejects It

  • Confirm the certificate covers the required hostname.
  • Confirm the CloudFront alternate domain name matches.
  • Confirm the certificate is available in the required region.
Important CloudFront fact: ACM certificates used with CloudFront must be requested or imported in US East (N. Virginia), us-east-1.

Scenario 3 – CloudFront Domain Works but Custom Domain Does Not

If this works:

https://d1sw29gbt5oue5.cloudfront.net

but this doesn't:

https://www.equitek.net

check:

Route 53→A/AAAA Alias→Correct CloudFront Distribution

Also verify that the custom hostname is configured as a CloudFront alternate domain name.

Scenario 4 – Browser Shows Certificate Error

  • Check domain name.
  • Check certificate SANs.
  • Check certificate status.
  • Check certificate expiration.
  • Check CloudFront certificate association.

For example, a certificate covering www.equitek.net does not automatically cover api.equitek.net.

Scenario 5 – CloudFront Returns 403

Don't automatically assume HTTPS is the problem.

CloudFront
    ↓
Origin
    ↓
S3
    ↓
Bucket / Object Access

Possible causes include:

  • Incorrect origin
  • S3 access configuration
  • Incorrect object path
  • Missing default root object
  • Incorrect origin configuration

17. Strong 2–3 Minute Interview Answer

“Sure. The objective was to expose the application through a secure HTTPS URL rather than allowing users to access it through plain HTTP or an AWS-generated endpoint.

In our architecture, Route 53 handled DNS, AWS Certificate Manager handled the TLS certificate, CloudFront acted as the public HTTPS and CDN layer, and S3 hosted the static website content.

First, we requested a public certificate through ACM for the required domain names, such as equitek.net and www.equitek.net. ACM generated DNS validation records. Since the domain was hosted in Route 53, we created those CNAME validation records there. Once ACM verified domain ownership, the certificate status changed from Pending Validation to Issued.

Next, we configured CloudFront with the S3 content as the origin. We configured the viewer protocol policy to redirect HTTP requests to HTTPS. We also configured the required alternate domain name, such as www.equitek.net, and associated the ACM certificate with the CloudFront distribution.

After the CloudFront distribution was deployed, we configured Route 53 so that the application's domain name resolved to the CloudFront distribution using an Alias record. This allowed users to access the application using https://www.equitek.net instead of the CloudFront-generated domain name.

From a troubleshooting perspective, if HTTPS wasn't working, I would check the issue layer by layer — first DNS and Route 53, then the ACM certificate and domain validation, then CloudFront alternate domain configuration and certificate association, and finally the CloudFront-to-origin and S3 configuration.

The key point is that each service has a different responsibility: Route 53 provides DNS, ACM provides the certificate, CloudFront provides the secure public entry point and content delivery, and S3 provides the static content.”
