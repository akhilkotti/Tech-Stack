A practical step-by-step guide for creating IAM users, groups, customer-managed policies, inline policies, and Elastic Beanstalk service roles based on the current API-Dev, MyShift, SQS, S3, SNS, API Gateway, Cognito, Lambda, and Elastic Beanstalk permissions.

1. Overview

Objective: Set up AWS IAM access for Ajay, Prajwal, Hitoshi, the API-Dev group, and the Elastic Beanstalk service role while keeping permissions organized and as close to least privilege as practical.

2. Create the IAM Group: API-Dev

The API-Dev group should contain permissions that are common to developers who work with the API/application platform.

Step-by-step

  1. Sign in to the AWS Management Console.
  2. Open IAM.
  3. Select User groups from the left navigation.
  4. Click Create group.
  5. Enter the group name: API-Dev.
  6. Select the required policies.
  7. Review the permissions and click Create group.

Why use a group?
If multiple developers need the same set of permissions, adding them to API-Dev is easier to maintain than attaching the same policies individually to every user.

3. Create Ajay's IAM User

Create the user

  1. Go to IAM → Users.
  2. Click Create user.
  3. Enter username: Ajay.
  4. Configure the required AWS Console and/or programmatic access according to your organization's access model.
  5. Add Ajay to the API-Dev group.
  6. Review and create the user.

Ajay's Group Permissions

Because Ajay belongs to API-Dev, he automatically receives:

  • AmazonCognitoPowerUser
  • AmazonCognitoReadOnly
  • AmazonESCognitoAccess
  • AmazonOpenSearchServiceCognitoAccess
  • AmazonS3ObjectLambdaExecutionRolePolicy
  • AWSLambda_ReadOnlyAccess
  • s3-access-to-image-bucket

Add Ajay's Direct Permissions

  1. Open IAM → Users → Ajay.
  2. Open the Permissions tab.
  3. Click Add permissions.
  4. Select the option to attach policies.
  5. Attach AmazonSNSFullAccess.
  6. Attach IAMUserChangePassword.

Prajwal currently has the customer inline policy:

s3-full-access-myshift-profile-images

  1. Open Prajwal → Permissions.
  2. Select Add permissions.
  3. Select Create inline policy.

6. Create a Customer-Managed Policy

Use a customer-managed policy when you need a reusable, organization-specific permission set.

Example: S3 Image Bucket Policy

  1. Go to IAM → Policies.
  2. Click Create policy.
  3. Select S3.
  4. Choose only the required actions, such as List, Get, Put, or Delete.
  5. Specify the exact image bucket as the resource.
  6. Review the policy.
  7. Give it a meaningful name, for example s3-access-to-image-bucket.
  8. Click Create policy.
  9. Attach the policy to the API-Dev group.
Preferred approach: Create reusable customer-managed policies for permissions that need to be shared by multiple users or groups.

Typical Policy Design

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:PutObject"
      ],
      "Resource": "arn:aws:s3:::YOUR-BUCKET-NAME/*"
    }
  ]
}

Note: Replace the bucket ARN with your actual bucket and include only the actions that the application genuinely requires.

7. Create the Elastic Beanstalk IAM Role

An IAM role is different from a user. The Elastic Beanstalk service can assume the role to perform AWS operations required to manage the environment.

Create the Role

  1. Go to IAM → Roles.
  2. Click Create role.
  3. Select AWS service as the trusted entity type.
  4. Select Elastic Beanstalk as the service/use case.
  5. Attach the required Elastic Beanstalk policies.
  6. Name the role aws-elasticbeanstalk-service-role.
  7. Review the trust relationship and permissions.
  8. Click Create role.

8. Configure the Elastic Beanstalk Environment

  1. Open the AWS Elastic Beanstalk console.
  2. Select your application.
  3. Select the required environment.
  4. Open Configuration.
  5. Locate the environment's IAM/service-role configuration.
  6. Select or configure aws-elasticbeanstalk-service-role where appropriate.
  7. Save the configuration.
Important distinction: Elastic Beanstalk can involve more than one IAM role. The Elastic Beanstalk service role and the EC2 instance profile have different purposes and should not automatically be treated as interchangeable.
Elastic Beanstalk │ ├── Service Role │ ├── Beanstalk management permissions │ ├── Enhanced health │ ├── Managed updates │ └── Environment management │ └── EC2 Instance Profile └── Permissions used by application EC2 instances

11. IAM Best Practices

  1. Prefer groups for common user permissions. Avoid repeatedly attaching the same policies directly to multiple users.
  2. Follow least privilege. Grant only the AWS actions and resources actually required.
  3. Restrict S3 policies to specific buckets and objects. Avoid Resource: * when it is not necessary.
  4. Review full-access policies. Policies such as AmazonSNSFullAccess and AmazonEC2FullAccess may be broader than necessary.
  5. Prefer customer-managed policies for reusable application-specific permissions.
  6. Use roles for AWS services and applications. Do not use long-lived IAM user credentials for workloads when a role can be used.
  7. Review inline policies carefully. If the same inline policy is needed by several identities, consider converting it into a customer-managed policy.
  8. Separate development and production access. Developers should not automatically receive unrestricted production permissions.
  9. Review IAM Access Advisor and CloudTrail data periodically. Remove permissions that are no longer required.
  10. Use MFA and your organization's preferred centralized identity/access-management approach.
Recommended pattern:

User → Group → Reusable Policies
AWS Service/Application → Role → Least-Privilege Policies

This structure makes access easier to understand, audit, maintain, and revoke.
